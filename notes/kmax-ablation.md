# K_MAX 消融：tile 接缝的真正成因，以及一处结论更正

> 本文记录一次**证伪性实验**。它推翻了两条此前写在 `results.md` 与
> `training-log.md` 里的结论，并说明交付模型的指标**被一个可避免的实现上限压低了**。

---

## 1. 背景：一处自相矛盾的记录

项目里原本有这样两条陈述：

| 位置 | 原文 |
|---|---|
| `notes/results.md` §4 第 2 条 | `K=128` 时可见明显正矩形接缝，**`K=256` 基本消除**（相对 K=1024 偏差仅 **−1.4%**） |
| `notes/training-log.md` §4 第 2 行 | 首版渲染出现正矩形块状接缝 → 根因"每 tile 候选截断 `K_MAX=128`" → 处置"改为 `K_MAX=256`" |

这两条都来自 **iteration 700** 的探针（`notes/kmax_probe_700.png`）——那是**冒烟测试**
的检查点。

但直接查看交付检查点的渲染图（iteration 7000 与 15000）时，**16×16 的矩形接缝
清晰可见**。记录与产物冲突。要么记录错了，要么交付检查点出了新问题。
必须做一个能证伪的实验来区分。

## 2. 机制：K_MAX 是怎么生效的

`cpu_port/diff_gaussian_rasterization/__init__.py`：

```
L81   _KMAX_DEFAULT   = int(os.environ.get("DSH_3DGS_KMAX", "128"))
L82   _BUDGET_DEFAULT = int(os.environ.get("DSH_3DGS_BUDGET", "6000000"))
...
L443  kmax = min(_KMAX_DEFAULT, counts_max)
L446  kmax_budget = max(1, _BUDGET_DEFAULT // (n_tiles * BLOCK_SIZE))
L447  kmax = max(1, min(kmax, kmax_budget))
```

关键点有三个：

1. **有效上限是三重取小**：`min(K_MAX, counts_max, BUDGET // (n_tiles × 256))`。
   `counts_max` 是"实际候选数最多的那个 tile 有几条候选"——也就是说，
   **如果 `counts_max ≤ K_MAX`，这个上限根本没有生效**，渲染与不限流等价。
   （`counts_max` 可以直接测出来，不必反推：**交付检查点上它约为 11,000**，
   所以 K=256 实际丢掉了最忙 tile 的 **97.7%** 候选。实测见 §8。）
2. **只抬 `K_MAX` 不够**，必须同时抬 `BUDGET`；否则第 446 行会把它钳回去。
   245×136 的渲染有 `ceil(245/16) × ceil(136/16) = 16 × 9 = 144` 个 tile，
   所以上游默认 `BUDGET=6e6` 只允许 `6000000 // 36864 = 162` —— **比 256 还低**。
3. 截断按 tile 独立进行：每个 tile 丢掉自己第 `kmax` 名之后的候选。
   于是相邻 tile 用了略微不同的高斯集合来合成，**接缝必然落在 tile 边界上**，
   即 x、y 为 16 的倍数的位置。

这第 3 点是本实验能够定量化的基础：接缝不是随机噪声，它有**已知的周期性位置**。

项目里所有交付脚本（`deliver_remaining.ps1`、`run_eval_holdout.ps1`、
`tail_pipeline.ps1`）都设的是 `KMAX=256 / BUDGET=16000000`，即
`kmax_budget = 16000000 // 36864 = 434`，故基线有效上限
= **`min(256, counts_max)`**。

## 3. 实验设计

**可证伪假设**：如果 `K_MAX=256` 是接缝的成因，那么把有效上限抬到 1024 之后，
接缝应当减弱、指标应当改善。反之，如果抬到 1024 后渲染**完全不变**，
说明 256 从未生效，接缝另有原因（那将是一个更严重的实现 bug）。

- **对照量**：只改 `K_MAX`（256 → 1024）与 `BUDGET`（16e6 → 37748736），
  其余全部不变——同一检查点 `truck_full/iteration_15000`、同一组相机、
  同一分辨率 245×136、同一代码路径。
- **非破坏性**：渲染写入**兄弟目录** `output/truck_full_k1024`，
  `output/truck_full` 的 K=256 基线渲染一个字节都没动。
- **量测方式**：除了 PSNR/SSIM/LPIPS，另加两项刻意的直接量测——
  - `tools/seam_metric.py`：**接缝比率** = tile 边界处的平均梯度 / tile 内部
    的平均梯度（按 16px 网格分类每一列/每一行）。
  - `tools/diff_renders.py`：逐像素解码比对，量化"改了多少"。

复现：`powershell -File tools\kmax_ablation.ps1 -K 1024`

## 4. 结果

### 4.1 接缝比率：接缝确实存在，且确实由 K_MAX 造成

tile 边界梯度 / tile 内部梯度（比值越接近 1 越干净）：

| 渲染 | 横向比率 | 纵向比率 |
|---|---|---|
| K=256 @ iteration 15000（**交付基线**） | **3.097** | **2.165** |
| K=1024 @ iteration 15000（消融） | **1.193** | **1.095** |
| **K=2048 @ iteration 15000（收敛）** | **1.044** | **1.025** |
| K=256 @ iteration 7000 | 3.082 | 2.088 |

K=256 时，落在 tile 边界上的像素跳变是 tile 内部的 **3.1 倍**。
抬到 K=1024 后降到 **1.19 倍**，K=2048 降到 **1.04 倍**（即收敛）。
假设成立。（K=2048 这一档是后续补测的，见 §8——它同时说明
**K=256 丢弃的候选远比"轻微"要多**：最忙的 tile 有约 11,000 个候选，
K=256 只留 256 个。）

### 4.2 指标：截断在丢真实贡献，不是"轻微偏差"

同一检查点、同一划分（train，251 视图）：

| 配置 | PSNR↑ | SSIM↑ | LPIPS↓ |
|---|---|---|---|
| K=256（交付基线） | 17.6287 | 0.5941 | 0.4144 |
| **K=1024（消融）** | **17.8468** | **0.6366** | **0.3505** |
| 变化 | **+0.2181 dB** | **+0.0425** | **−0.0639** |
| K=2048（收敛口径） | 17.7620 | 0.6351 | 0.3512 |

K=2048 那一行**不是**单调延续 K=1024 的趋势（PSNR 反而低 0.085 dB）。
这不是测量错误，原因见 §8.3.1：**权重是在 K=256 下训练出来的**，
指标不随 K 单调改善。但**接缝**是单调改善并最终消失的
（3.10 → 1.19 → 1.04），这才是本节要测的量。

原文档说的"**−1.4%**"是 iteration 700 的数字。在交付检查点上，
LPIPS 的改善幅度是 **−15.4%**（0.4144 → 0.3505），完全不是"轻微"。

### 4.3 逐像素差异：几乎所有像素都受影响

`tools/diff_renders.py` 对比 K=256 与 K=1024 的 251 张渲染：

| 量 | 值 |
|---|---|
| 有差异的文件 | **251 / 251** |
| 平均每像素绝对差（按文件平均） | **10.7069 / 255**（≈ 4.2% 满量程） |
| 最差单像素差 | **242 / 255** |
| 最差文件 | `00067.png`，平均差 17.54 / 255 |

一张图里平均每像素偏 4%，最差 95%——这是**结构性**差异，不是舍入噪声。

### 4.4 视觉证据

`notes/probe/seam_compare_00051.png`：同一次渲染的同名视图 `00051.png`
（该视图是差异最大的一张），裁出接缝最强的区域，5× 最近邻放大，
红色线是 16px tile 网格。

- **左（K=256）**：车身上的明暗过渡在 tile 边界处出现硬跳变，
  深色竖带、门板上的横向台阶、左下角车轮的涂抹感——**都对齐红色网格线**。
- **右（K=1024）**：同样的区域是连续渐变，无块状边界。

完整 4 视图对照见 `notes/probe/kmax_truck_full_15000_K1024.png`。

### 4.5 成本

| | K=256 | K=1024 |
|---|---|---|
| 渲染 251 视图耗时 | ≈45 s（≈0.18 s/视图） | **2.1 min（≈0.50 s/视图）** |
| 峰值工作集 | ~0.5 GB | **1.88 GB** |

约 2.8× 的渲染时间、约 4× 的 `[T,256,K]` 张量内存。在 15.7 GB 的机器上
渲染完全可行（实测空闲内存 4.4 GB）；训练时会更吃紧，这大概也是当初选 256 的原因。

## 5. 更正

| # | 原结论 | 更正 |
|---|---|---|
| 1 | "`K_MAX=256` **基本消除**接缝"（`results.md` §4） | **不成立，而且连它自己那个检查点都不成立。** K=256 在 iteration 15000 的接缝比率是 3.10 / 2.17，在 iteration 700 更是 **5.01 / 2.28**；只有 K=2048 才降到 1.04 / 1.03（收敛）。旧结论**不是**"上限没生效"——实测 iteration 700 的 `counts_max` 高达 20,618–38,481，上限咬得比 15000 更狠——而是**旧探针测的全图均值对 tile 接缝这种空间结构化伪影不敏感**。完整实测见 §8 与 §9。 |
| 2 | "相对 K=1024 偏差仅 **−1.4%**"（`results.md` §4、`training-log.md` §5） | 交付口径（iteration 15000）下是 **PSNR +0.22 dB / SSIM +0.043 / LPIPS −0.064**，平均每像素差 4.2%。**但不要把"−1.4% → +0.22 dB"读成"代价随训练增长"**——旧数字用的是对伪影不敏感的**全图均值**，两者不可直接比较（见 §9）。 |
| 3 | `training-log.md` §4 #2 把"接缝"记为**已处置** | 应记为**已定位、已量化、在交付口径上已修复**（消融证明 K=1024 可解）；但**交付基线仍跑在 K=256 上**。 |
| 4 | 各处把 `K_MAX` 的影响称为"轻微"/"−1.4%" | **严重低估**。实测（§8）最忙 tile 有约 **11,000** 个候选，`K_MAX=256` 丢掉 **97.7%**，且平均每 tile 1,478 个候选意味着**大多数 tile 都在截断**。`K_MAX` 是 CPU 路径的核心近似，不是一个小旋钮。 |
| 5 | "前向对齐 2.4e-07"被用来支持"与 CUDA 数值等价" | 该对齐验证的是**给定候选集下单次光栅化调用**的等价性，**不覆盖候选集被截断**这一层近似。表述应收窄。 |

**产生这条错误记录的机制值得记一下**——它由两个独立的失误叠加而成：

1. **用了一个对目标现象不敏感的代理量。** 旧探针报告的是全图均值，而接缝是
   空间上集中在 tile 边界的一阶不连续。见 §9：在它**自己那个** iteration 700
   检查点上，K=256 的接缝比率是 **5.01**（15000 上是 3.10），
   可全图均值只差 1.4%。
2. **在一个非最终检查点上标定。** 即便代理量选对了，早期检查点也不能代表
   交付检查点。

原稿把原因写成"上限只在场景变密之后才开始咬合"——**这也是错的**：
实测 iteration 700 的 `counts_max` 是 20,618–38,481，比 15000 的 11,104 **更大**，
上限当时咬得最狠。

**教训：被测量必须直接对应目标现象；标定必须在最终检查点上做。两者缺一不可。**

## 6. 这条结论对项目整体数字的影响

`results.md` §2.1 与 `README.md` 的头条数字（PSNR 17.63 / SSIM 0.594 / LPIPS 0.414）
是 **K=256 口径**，因此**低估了本复现的实现质量**。K=1024 口径为
**17.85 / 0.637 / 0.351**。

需要说清的是：**这不是"调参刷分"**。K_MAX 是一个纯工程性的内存护栏，
不是论文算法的一部分——论文的 CUDA 光栅器**没有这个上限**。
把 K 抬高只是让 CPU 复现更接近它所对标的算法。

但按 §8 的实测，"更正确的口径"应当更准确地表述为：

- **K=2048 是收敛口径**（接缝 1.044，K=1024 → K=2048 像素变化仅 0.51/255）；
- **K=1024 已很接近**，但仍残留可见的接缝结构（1.19）；
- **K=256 是重度欠采样**（丢掉最忙 tile 的 97.7% 候选，接缝 3.10）。

三个口径的**指标并不单调**（§8.3.1），因为权重是在 K=256 下训练出来的，
所以不能简单地说"K 越大数字越好看"。接缝这个**结构性**伪影是单调改善的。

同时，训练本身仍是在 K=256 下完成的（梯度也来自截断后的光栅器）。
训练/渲染口径的这一处不一致已在此记录，不影响 §2.2 的泛化间隙结论
（间隙是在同一渲染口径内测的）。

## 7. 在留出集模型上复验

为了确认第 4 节不是 `truck_full` 的个例，把**留出集模型**
（`truck_eval`，iteration 7000）也用 K=1024 重渲染，并**两个划分都测**：

```
powershell -File tools\kmax_ablation.ps1 -Source output\truck_eval `
    -Iteration 7000 -K 1024 -BothSplits
```

### 7.1 接缝在留出集上同样存在、同样被消除

| 模型 / 划分 | 视图 | K_MAX | 横向比率 | 纵向比率 |
|---|---|---|---|---|
| `truck_eval` train | 219 | 256 | **3.099** | **2.086** |
| `truck_eval` train | 219 | 1024 | 1.298 | 1.128 |
| `truck_eval` test（留出） | 32 | 256 | **3.359** | **2.244** |
| `truck_eval` test（留出） | 32 | 1024 | 1.321 | 1.154 |

K=256 下，**留出集的接缝甚至比训练集更重**（3.359 vs 3.099）——
这合理：留出视图的相机位置模型没见过，预测的高斯覆盖更松散，
每个 tile 需要更多候选来收敛，于是截断丢得更多。

### 7.2 配对指标：间隙略微收窄

| 划分 | 视图 | K_MAX | PSNR↑ | SSIM↑ | LPIPS↓ |
|---|---|---|---|---|---|
| train | 219 | 256 | 16.0572 | 0.5645 | 0.4368 |
| **test（留出）** | **32** | 256 | **15.2789** | **0.5235** | **0.4639** |
| *间隙* | | *256* | *−0.778 dB* | *−0.041* | *+0.027* |
| train | 219 | 1024 | 16.0359 | 0.5951 | 0.3807 |
| **test（留出）** | **32** | 1024 | **15.3970** | **0.5674** | **0.3991** |
| *间隙* | | *1024* | *−0.639 dB* | *−0.028* | *+0.018* |

- **留出集绝对指标改善**：PSNR **+0.118 dB**、SSIM **+0.044**、LPIPS **−0.065**。
- **train/test 间隙收窄**：0.778 → **0.639 dB**。
  两个口径下间隙都在 0.6–0.8 dB 这个量级，**泛化间隙很小的结论是稳健的**，
  不随光栅器口径变化——这从另一个方向支持了"欠拟合而非过拟合"的判定。

### 7.3 一处诚实的保留：train 划分的 PSNR 略微下降

注意上表中 `train` 行的 PSNR 是 **16.0572 → 16.0359（−0.021 dB）**，
而同一行的 SSIM（+0.031）与 LPIPS（−0.056）都改善了。

也就是说抬 K **不是单调改善 PSNR**。一个自洽的解释是：这个模型是在
K=256 的截断光栅器下训练出来的，它的高斯已经**适应**了那套截断；
在渲染时撤掉截断，感知类指标（SSIM/LPIPS）明显变好，但逐像素误差
可以局部变差。这是一个真实的、值得记录的**训练/渲染口径不一致**，
而不是噪声（渲染是确定性的）。

它不影响本文的主结论：无论哪个口径，间隙都是 0.6–0.8 dB，
而与论文的差距是 7.7 dB——量级差十倍。

### 7.4 复验结论

接缝现象在**两个模型、两个划分**上都复现，且都由 K=1024 消除。
第 5 节的更正不是个例，可以推广到整个项目。

## 8. 这个上限到底丢掉了多少：`counts_max` 实测

第 2 节说"有效上限 = `min(K_MAX, counts_max, BUDGET//…)`"。前面几节都是
**从行为反推**这个上限在起作用。但 `counts_max` **不依赖 `K_MAX`**——
它是场景自身的属性，可以直接测出来。测出来之后，这个问题的量级完全变了。

工具：`tools/raster_cap_probe.py`（打开光栅器自带的调试输出，
一次前向即报告 `pairs` / `counts_max` / 实际生效的 `kmax`）：

```
python tools/raster_cap_probe.py --model output/truck_full --iteration 15000
```

### 8.1 实测结果

`truck_full`，train camera #0，245×136（144 个 tile）：

| 检查点 | 高斯数 | 视锥内 kept | 总 (高斯,tile) 对 | **平均每 tile** | **counts_max** |
|---|---|---|---|---|---|
| 7000 | 89,851 | 79,998 | 192,099 | 1,334 | **10,941** |
| 15000 | 87,475 | 78,609 | 212,843 | **1,478** | **11,104** |
| 30000 | 87,475 | 78,782 | 284,404 | 1,975 | **12,100** |

不同相机（iteration 15000）：`counts_max` = 9,323 / 11,104 / 13,462 / 14,440
（view 180 / 0 / 60 / 120）——**同一量级，view 0 不特殊**。

### 8.2 这意味着什么

- **最忙的那个 tile 有 11,104 个候选，而 K=256 只保留 256 个——丢掉了 97.7%。**
  K=1024 也只保留 9.2%。
- **平均每 tile 就有 1,334–1,975 个候选**，也就是说 **K=256 下大多数 tile
  都在截断**（远不止个别边界 tile）。这才是接缝如此明显的原因。
- `counts_max` 在 7000 就已经是 10,941——**上限从 7000 起就一直在重度生效**。
  （iteration 700 的检查点**本机还在**（`output/truck_smoke`），可以实测。
  结果见 §8.5：它比 15000 咬得**更狠**，而这直接推翻了本文档早先给出的
  "700 次迭代时上限尚未越界"这一解释。）

### 8.3 K=1024 也还在截断——但它已接近收敛

K=1024 只保留最忙 tile 的 9.2%，所以它**也还在重度截断**。
第 4.1 节测到的 K=1024 接缝比率是 1.19（理想值 1.0）——与"残留截断"一致。

但"还在截断"不等于"离收敛很远"。为了把这一点测准，又渲染了 **K=2048**，
并把三组渲染两两做逐像素比对（`tools/diff_renders.py`）：

| 对比 | 平均每像素差 | 接缝比率（横 / 纵） |
|---|---|---|
| K=256 → K=1024 | **10.7069** / 255 | 3.097 → 1.193 |
| K=1024 → K=2048 | **0.5095** / 255 | 1.193 → **1.044** |
| K=256 → K=2048 | 11.2163 / 255 | 3.097 → 1.044 |

**K=1024 → K=2048 的像素变化比 K=256 → K=1024 小 21 倍**，
且接缝比率降到 **1.044 / 1.025**——**K=2048 实质上就是收敛渲染**。

所以更准确的说法是：

- **K=256 是重度欠采样**：相对收敛渲染平均差 **10.7/255**，接缝比率 3.10；
- **K=1024 已相当接近收敛**：平均只差 **0.51/255**，
  但**残余的接缝结构仍然可见**（1.19 vs 1.04）；
- **K=2048 收敛**：接缝消失（1.04 / 1.03）。

> **一个方法论要点**：上面"平均只差 0.51/255"与"接缝仍可见"并不矛盾。
> 接缝是**空间上高度集中**的伪影，它对**平均**像素差的贡献很小，但人眼很敏感。
> **用平均差（或平均值指标）去判断接缝是否存在是错的**——
> 这正是当初"−1.4%"这类平均口径会漏掉这个问题的原因，
> 也是为什么这里要专门用 `tools/seam_metric.py` 按 tile 网格分别统计梯度。

### 8.3.1 指标并未随 K 单调改善（一个诚实的异常）

| K_MAX | PSNR↑ | SSIM↑ | LPIPS↓ | 接缝（横 / 纵） |
|---|---|---|---|---|
| 256 | 17.6287 | 0.5941 | 0.4144 | 3.097 / 2.165 |
| 1024 | **17.8468** | **0.6366** | **0.3505** | 1.193 / 1.095 |
| 2048 | 17.7620 | 0.6351 | 0.3512 | **1.044 / 1.025** |

接缝**单调减少**（3.10 → 1.19 → 1.04），但 PSNR/SSIM 在 K=1024 处最高，
到 K=2048 反而略降（−0.085 dB / −0.0015）。LPIPS 基本持平。

原因很可能是：**这个模型的权重是在 K=256 的截断光栅器下训练出来的**，
它已经适应了那套截断。在渲染时逐步撤掉截断，感知类指标先变好，
但逐像素误差在越过某个点后会小幅回弹——因为模型从未在"无截断"的
前向语义下被优化过。

这**不影响**本文的核心结论（K=256 有可测量的、可消除的接缝伪影），
但它说明一件重要的事：**`K_MAX` 与训练出的权重是耦合的**，
不能把它当成一个纯粹的"后处理开关"来讨论。

### 8.4 为什么不能直接不限流

完全不截断需要 `K ≈ counts_max ≈ 11,000–14,000`。但 `[T, 256, K]` 这一族中间
张量（`cpu_port/diff_gaussian_rasterization/__init__.py` 的
L509–529：`d_x`/`d_y`/`cn`/`power`/`alpha`/`log_om`/`csum`/`t_excl`/`weighted`）
在 K=11,104 时**每个约 1.56 GB**，同时存活 6–9 个，即 **约 10–15 GB**——
本机（15.7 GB 总量、渲染时约 6.5 GB 可用）**放不下**。

这解释了当初为什么设 `K_MAX`：它不是一个随意的旋钮，而是
**CPU 近似 CUDA 时的内存换质量折衷**。但它的代价被严重低估了：
文档原称"相对 K=1024 偏差仅 −1.4%"，实测在交付检查点上是
**接缝比率 3.10、逐像素差 4.2%、LPIPS 差 0.064**。

**正确的结论应当是**：本复现的渲染质量受这一折衷限制，
而不是"已经与 CUDA 数值等价"。前向 2.4e-07 的对齐结论是对
**单次光栅化调用在给定候选集下**的验证，不覆盖"候选集被截断"这一层近似。

## 9. 回到 iteration 700：旧结论在自己的检查点上就是错的

第 5 节原来给的解释是"旧结论来自 iteration 700，那时 `counts_max` 还没越过 256，
上限几乎不生效"。**这个解释是错的，而且我当时并没有测过它。**
`output/truck_smoke` 里的 iteration 700 检查点仍在本机，直接测：

### 9.1 `counts_max` 在 700 比在 15000 更大

smoke 模型按它自己的 `cfg_args`（`resolution=8` → 122×68，**40** 个 tile）：

| 相机 | 高斯数 | 视锥内 | 总对数 | 平均每 tile | **counts_max** |
|---|---|---|---|---|---|
| view 0 | 136,029 | 106,942 | 205,573 | 5,139 | **25,293** |
| view 60 | 136,029 | 102,354 | 198,648 | 4,966 | **28,033** |
| view 120 | 136,029 | 103,938 | 192,559 | 4,814 | **38,481** |
| view 180 | 136,029 | 99,878 | 190,252 | 4,756 | **20,618** |

**iteration 700 的 `counts_max` 是 20,618–38,481，比 iteration 15000 的 11,104
还大。** `K_MAX=256` 当时保留的是最忙 tile 的 **0.7%–1.2%**——
比交付检查点**咬得更狠**。

所以"700 时上限没生效"完全不成立。**上限从最早的探针起就一直在重度生效。**

### 9.2 那时接缝也照样在（而且更重）

用同一套 `tools/seam_metric.py` 测 iteration 700 的渲染
（`output/truck_smoke_k256` / `_k1024`，251 视图）：

| K_MAX | 横向比率 | 纵向比率 |
|---|---|---|
| 256 | **5.007** | 2.277 |
| 1024 | **3.672** | 2.202 |

**iteration 700 的 K=256 接缝（5.01）比 iteration 15000 的（3.10）更严重。**
而且那时即使抬到 1024 也仍然很差（3.67）——因为 `counts_max` 高达 2–4 万，
1024 只覆盖了 3%–5%。

### 9.3 那么旧探针为什么会得出"K=256 基本消除接缝"？

因为**它测的量看不见接缝**。旧探针（`tools/kmax_probe.py`）报告的是一个
**标量均值**（`mean`，从 0.3743 到 0.5806）。而接缝是**空间上高度集中**的伪影：
它体现在 tile 边界处的一阶不连续，对全图均值的影响很小。

这与 §8.3 的观察是同一件事的两面——那里我看到"平均像素差只 0.51/255"
却"接缝仍可见"。**一个全局平均量，无论它叫 `mean` 还是 PSNR，
都不能用来判断一个空间上结构化的伪影是否存在。**

### 9.4 教训（比 K_MAX 本身更值钱）

原来的推理链是：
> "K=128 有接缝 → 抬到 256 → 探针的均值只差 1.4% → 所以 256 基本消除了接缝"

其中**每一步都有问题**：
1. **没有直接测接缝**，而是测了一个与接缝弱相关的代理量（全图均值）；
2. **没有在最终检查点上复验**（但这个具体错误不是"700 时上限没生效"，
   而是"700 时的探针指标本身就无效"——上限一直在生效）；
3. 把"代理量变化小"直接读成了"目标伪影已消除"。

正确做法就是本文所做的三件事，缺一不可：
**（a）被测量必须直接对应目标现象**（`seam_metric.py` 按 tile 网格分别统计梯度）；
**（b）在最终交付检查点上复验**；
**（c）给出可证伪的对照**（K=2048 收敛档，证明差异确实来自 K）。

## 10. 修复：把武断的数字换成内存预算

前面九节都在量化"固定 K 有多糟"。但"应该取多少"这个问题问错了——
正确的问法是**"这台机器能花多少内存"**，然后让 K 去填满它。

`K_MAX` 之所以存在，纯粹是因为 CPU 上 `[T,256,K]` 稠密张量放不下
（见 8.4）。那就直接以内存为自变量：给定预算 `MEM_MiB`、tile 数 `T`、
每个张量 `T×256×K` 个 float32，若峰值同时存活 `m` 个这样的张量，则

```
K = floor( MEM_MiB × 1024² / (m × T × 256 × 4) )
K = min(K, counts_max, CEILING)
```

### 10.1 实现

`cpu_port/diff_gaussian_rasterization/__init__.py` 里新增 `resolve_kmax()`，
并在光栅化入口用它替换原来的两行取小：

```python
def resolve_kmax(n_tiles, counts_max):
    legacy_budget = max(1, _BUDGET_DEFAULT // (n_tiles * BLOCK_SIZE))
    if _KMAX_AUTO:
        bytes_per_k = _KMAX_LIVE_TENSORS * n_tiles * BLOCK_SIZE * 4.0
        by_mem = int(_KMAX_AUTO_MIB * 1024 * 1024 / max(bytes_per_k, 1.0))
        return max(1, min(counts_max, by_mem, _KMAX_CEILING)), legacy_budget
    return max(1, min(min(_KMAX_DEFAULT, counts_max), legacy_budget)), legacy_budget
```

启用方式（`DSH_3DGS_KMAX` 默认仍是固定的 `128`，旧结果逐位可复现）：

```powershell
$env:DSH_3DGS_KMAX        = "auto"
$env:DSH_3DGS_KMAX_MEM_MB = "2048"
```

### 10.2 预算换算出的 K（truck，245×136，144 个 tile）

| `DSH_3DGS_KMAX_MEM_MB` | 推导出的 K | 与 `counts_max`=11,104 的关系 |
|---|---|---|
| 512 | 455 | 仍截断 |
| 2048 | 1,820 | 仍截断，但已越过收敛区 |
| 8192 | 7,281 | 仍略低于 11,104 |

作为对照，旧路径的 `legacy_budget` 在这台机器上只有 **162**——这就是为什么
不抬 `DSH_3DGS_BUDGET` 时 K 永远上不去。`auto` 模式下该预算不再参与。

### 10.3 验证：auto 复现了 K=2048 的收敛画质

固定 view 51、同一次迭代（15000）、只改 K，用 `seam_metric.py` 量同一张图上
的 tile 边界梯度比（1.0 = 干净）：

| 配置 | 实际 K | H 比率 | V 比率 |
|---|---|---|---|
| 固定 256 | 256 | 3.666 | 2.136 |
| 固定 1024 | 1,024 | 1.553 | 1.087 |
| 固定 2048 | 2,048 | 1.254 | 1.045 |
| **auto，2 GiB** | **1,820** | **1.254** | **1.048** |

`auto` 用 1820 就拿到了 2048 的效果——因为超过收敛点之后 K 本来就不再是瓶颈。
（单视图的数字比 §4 的 251 视图均值更重，因为 view 51 是较难的视角；
两者只用于同条件 A/B，不要跨表比较。）

### 10.4 局限，写清楚

- `DSH_3DGS_KMAX_TENSORS`（默认 8）是**按代码结构估算**的峰值存活张量数，
  不是实测值。它直接线性影响推导出的 K：高估则偏保守，低估则可能 OOM。
  它作为环境变量暴露出来，就是为了让使用者在自己的机器上校准。
- 预算是**建议值**，不是硬保护。真的超了，你会拿到 OOM 而不是优雅降级。
- 本文所有已发布数字仍然来自**固定 K**，因为那是可复现的；
  `auto` 是"下一轮该怎么跑"的建议，不是对既有结果的替换。
- `DSH_3DGS_KMAX_TENSORS` 的默认 8 是**推理**口径（`torch.no_grad()`）。
  训练时带 autograd，实测必须显著调大，否则 `auto` 会在训练里选出一个跑不动的 K
  ——见 §11 的否定结果。

## 11. 一个否定结果：K=1024 **训练**在这台机器上跑不动

§10.4 说 `auto` 的预算按推理时（`torch.no_grad()`）的张量存活数估算。
**训练时带 autograd，这个数字要大得多**——实测直接撞上机器的提交上限。

为消除"训练用 K=256、打分用 K=1024"的口径不一致（§7），我按 §7 的协议原样重跑，
只把 `K_MAX` 换成 1024（`tools/run_eval_holdout_k1024.ps1`，其余参数逐项相同）：

| 指标 | K=256 基线（已交付的 `truck_eval`） | K=1024 重训 |
|---|---|---|
| 迭代速率 | 0.447 s/it（7000 次 = 52.1 min） | **4.38 s/it** |
| 7000 次推算耗时 | 52 min | **约 8.5 h** |
| 启动前空闲物理内存 | — | 5.15 GB |
| 运行中空闲物理内存 | — | **0.44 GB** |
| 提交电荷 / 上限 | — | **29.36 / 29.72 GB** |
| 页面文件峰值 | — | 3.40 GB |

**慢的原因不是算法，是内存。** 带 autograd 的合成阶段同时保活的 `[T,256,K]`
张量远多于 8 个，K=1024 时每个 144 MB，很快把提交电荷推到 29.36 GB，
距上限只剩 **0.36 GB**。系统随即进入持续换页，吞吐掉到基线的 **1/9.8**。
在 30 次迭代后终止，不产出检查点。

### 11.1 这条否定结果排除了什么

它排除了最省事的那条补救路径——"再按 K=1024 跑一遍就对齐了"。
在这台机器上，**不存在既自洽又收敛的 K**：

- 接缝收敛需要 K ≥ 1024（§4.1：1024 才到 1.19，2048 到 1.04）；
- 训练在 K=1024 放不下（本节实测）。

两者无法同时满足。所以交付数字保留 §7 的口径披露（训练 K=256、打分 K=1024），
而不是假装一致——这是当前硬件下的诚实上限，不是偷懒。

### 11.2 对 §10 的修正

`DSH_3DGS_KMAX_TENSORS=8` 这个估算**只对推理成立**。要拿 `auto` 去做训练预算，
必须按实测显著调大（本机至少 12–16），否则 `auto` 会在训练里选出一个跑不动的 K，
表现出来就是本节这样的换页。这不是公式错，是那个常数默认值只覆盖了一半场景。
